Verification performed for this review: the full run was reproduced locally from the branch's code (`.venv/bin/python train_gui_agent.py --device cpu --outdir ...`, seed 0, 268 s here vs 213.5 s reported) and the printed summary table is **identical** to the one printed in the lab page and in the code README (sparse 0.000/0.000/16.00/0.000/0.005, curriculum 0.328/0.391/12.09/0.565/0.435, shaped 0.141/0.172/14.77/0.459/0.522, hackable 0.000/0.000/16.00/1.000/6.173). `pytest code/chapter22_computer_use -q` gives "22 passed, 7 subtests passed", as the report claims. The per-episode CSVs also confirm the narrative numbers ("16 lucky successes in 3000 episodes" for sparse; curriculum promotions at episodes 1000/4000/7500; final-1000-episode stochastic success 0.366; shaped greedy success 0.047 at episode 12000 and 0.141 at 15000; hackable submit share 0.092 -> 0.977 and mean reward 0.671 -> 6.104 over the first/last 500 episodes). The reported results are genuine and reproducible.

## Errors

1. `docs/chapter22_computer_use/lab.md` (Reward modes) — "`shaped_hackable` adds +0.4 for _every_ submit click, right or wrong -- the deliberate bug." — This misdescribes the code. In `code/chapter22_computer_use/gui_env.py` (`MiniFormEnv.step`) the bonus is added only in the _failure_ branch of the submit handler: `if success: done = True; reward += SUBMIT_REWARD` / `else: ... reward += SUBMIT_BONUS`. A **correct** submit pays `SUBMIT_REWARD = 1.0` and _no_ 0.4 bonus; only a **wrong** submit pays `SUBMIT_BONUS`. The same false statement is repeated in the `gui_env.py` module docstring ("a deliberately hackable variant also pays for _any_ submit click") and in the inline comment ("Deliberate reward flaw: every submit click pays, right or wrong, so spamming submit without doing the work earns more than solving the task"). The page's own arithmetic is consistent with the _code_ (a solved task is worth ~1.7-1.95, not 1.0 + 0.4 + progress), which shows the phrase is a description error, not a computation error -- but it misstates the mechanism the whole lab is built to demonstrate, and no test catches it (`test_wrong_submit_hackable_pays` only exercises the wrong-submit path). — Suggested fix: write "adds +0.4 for every _failed_ submit click (a correct submit still pays only the +1 terminal reward)" in `lab.md`, in the `gui_env.py` docstring and in the inline comment, and add a test asserting that a correct submit in `shaped_hackable` pays exactly 1.0.

2. `docs/chapter22_computer_use/lab.md` (Results table) and `code/chapter22_computer_use/README.md` (reference table) — the table is introduced as "Greedy policy on the full task, last snapshot:" but the "mean reward" column is not from the greedy snapshot. In `train_gui_agent.py` every other column comes from `res["eval_log"][-1]` (the greedy evaluation), while `mean_reward` is `float(np.mean([e["reward"] for e in res["ep_log"][-200:]]))`, i.e. the mean undiscounted reward of the last 200 **stochastic training** episodes. The two differ visibly: for the hackable row the greedy policy submits on every step, so its snapshot reward is exactly 16 x (0.4 - 0.01) = 6.24, not the printed 6.173; for the sparse row the greedy reward is 0.000 while the table prints 0.005 (one lucky success in the last 200 training episodes); for the curriculum row the greedy mean reward is ~0.33 (its greedy success rate), not 0.435. The table therefore mixes two different measurement sources under one header. — Suggested fix: relabel the column "mean train reward (last 200 episodes)", or compute the reward of the greedy eval episodes and keep the header as is.

3. `docs/chapter22_computer_use/lab.md` (What to look for) — "Level 0 (one field plus submit) succeeds by luck ~10-15% of the time" — measured, this is ~8%, not 10-15%. Simulating the environment with a uniform-random policy over the 28 actions gives a level-0 success rate of 8.2% (20 000 episodes, SE 0.4%), and the actual untrained `PolicyNet` (seed 0) gives 8.8% (3 000 episodes, SE 0.5%). The same simulation gives 0.43% for the full level-3 task, which is consistent with the page's other "~0.5%" claim and with the observed "16 lucky successes in 3000 episodes" (16/3000 = 0.53%), so only the level-0 figure is inflated -- by a factor of 1.2-1.8. The qualitative point ("dense enough for the success filter to collect clean `type`-then-`submit` pairs") survives the correction. — Suggested fix: write "succeeds by luck ~8% of the time" (and, if a range is wanted, "8-9%").

4. `docs/chapter22_computer_use/lab.md` (Extension exercise 2) — "Lower `SUBMIT_BONUS` until the hackable run starts succeeding, and raise it until a shaped run breaks." — `SUBMIT_BONUS` is read only on the `shaped_hackable` path in `gui_env.py`; `train_mode()` maps the regimes to reward modes as `{"sparse": "sparse", "curriculum": "sparse", "shaped": "shaped", "hackable": "shaped_hackable"}`, so the `shaped` regime never sees the bonus and changing `SUBMIT_BONUS` cannot affect a shaped run at all. The hint's arithmetic is also off: the spam return is 16 x (bonus - 0.01) (each step pays -0.01), not "16 x bonus", and the crossing with a full solution (measured mean 1.72, max 1.95) is at bonus ~ 0.12-0.13. — Suggested fix: "raise it until the hackable run breaks (a shaped run is unaffected: the bonus is only read in the `shaped_hackable` mode)" and use 16 x (bonus - 0.01) in the hint.

5. `docs/chapter22_computer_use/lab.md` (Extension exercise 3) — "the 30-line BC probe in the report shows the net needs thousands of supervised steps on clean pairs" — there is no such probe in `planning/reports/ch22-lab.md`; the report only records one line, "Pilots: ... inline `python -c` BC probes (oracle demos -> 99% level-0, proving capacity; motivated replay volume)", with no code, no line count, and no result table. The hint therefore points the reader at an artifact that does not exist (and planning reports are not part of the published book). — Suggested fix: replace the reference with the actual instruction (e.g. "clone a few hundred oracle `type`/`submit` pairs for 10 epochs and watch the held-out success rate; the network can fit them, but it needs far more clean pairs than the lucky successes provide"), or drop the hint.

6. `docs/.vitepress/config.mjs` and `docs/chapter22_computer_use/lab.md` — the new page is not registered in the sidebar: the chapter-22 group in `config.mjs` still ends at `{ text: '22.2 Prompt Injection and Instruction Hierarchy', link: '/chapter22_computer_use/safety-swarm' }`, and `config.mjs` is not in the diff. `AGENTS.md` states "Every navigable page must be listed there"; the writer's own report lists the addition under "Sidebar additions" but says "Coordinator to add (config.mjs out of scope)", so it was never made. Consequences: the page is unreachable from the site navigation, and `scripts/fix-heading-numbers.mjs` only rewrites pages that appear in the sidebar (its regex is `text:\s*'((?:[A-Z]\.)?\d+(?:\.\d+)*)\s+([^']+)'` + `link:`), so the hand-invented "22.L" label is never checked against the sidebar. "22.L" is also a numbering convention that exists nowhere else in the book: a scan of every `title:` front matter finds no letter-suffixed section number, and the book's hands-on pages are numbered "N.M Hands-on: ..." (e.g. "19.8 Hands-on: Training a DeepCoder Agent with rLLM"). — Suggested fix: add `{ text: '22.3 Hands-on: Form-Filling GUI Agent', link: '/chapter22_computer_use/lab' }` to the chapter-22 group and run `npm run fix:headings` so the H1 and the front-matter title match the sidebar label.

## Doubts

1. `docs/chapter22_computer_use/lab.md` (Walkthrough) — "Every snapshot evaluates the greedy policy on the _full_ task over 64 train seeds and 64 held-out seeds from a disjoint range" — both evaluation blocks are disjoint from _every_ training seed: training uses `TRAIN_SEED_BASE + seed*1_000_000 + ep` = 1,000,000+ (seed 0), 2,000,000+ (seed 1), 3,000,000+ (seed 2), 4,000,000+ (seed 3), while the "train" evaluation uses `EVAL_SEED_BASE = 500_000` and the "held-out" evaluation uses `HELDOUT_SEED_BASE = 900_000`. So the column labelled "train success" is not measured on layouts the policy saw during training; the two columns differ only in which disjoint seed block is used, and the generalisation conclusion ("the policy reads labels from the observation rather than memorising layouts") still holds, but the naming invites the reader to read the first column as a training-set number. (With 64 seeds, the standard error on 0.33 is 5.9%, so 0.33 vs 0.39 is indeed "within eval noise" as claimed.) Consider renaming the splits ("seed block A/B") or training on the 500,000 block so "train" means what it says.

2. `docs/chapter22_computer_use/lab.md` (What to look for) — "the per-click bonus makes submit-spam (6.17) out-earn solving the task (~1.9)" — the 6.17 figure is right (the spam ceiling is 16 x (0.4 - 0.01) = 6.24 and the run reached 6.173), but the optimal solve is worth 1.72 on average, not ~1.9: simulating the optimal action sequence on 500 level-3 tasks gives mean 1.717, min 1.47, max 1.95. The reason is that a box target of the form "uncheck X" is _already_ satisfied at reset (`count_satisfied` counts it, and `best_satisfied` is initialised to that count), so it never pays the +0.25 progress reward; only the two field targets (and the boxes that must be checked) pay progress. 1.9 is the best case (both boxes checked, 25% of tasks). The comparison itself is unaffected, but a reader checking the arithmetic will not reproduce ~1.9 on a random task.

3. `docs/chapter22_computer_use/lab.md` (The update) — "Batched REINFORCE with a state-value baseline and standardised advantages, exactly the Chapter 6 update" — Chapter 6.2's update (`docs/chapter06_policy_gradient/pg-improvements.md`) is `advantages = returns_t - values_pred` followed by `policy_loss = -(log_probs * advantages).mean()`: it has neither the batch advantage standardisation nor the entropy bonus that the lab adds (`policy_loss = -(log_probs * advantages).mean() - entropy_coef * entropy.mean()`). The shown snippet does match the lab code, so this is a wording issue, but "exactly the Chapter 6 update" overstates the match; "the Chapter 6 update plus batch-standardised advantages and an entropy bonus" would be accurate.

4. `docs/chapter22_computer_use/lab.md` (Background) — "the hackable regime shows what Step 9 calls a verifier/reward failure: the metric goes up while the task does not" — Chapter 22 Step 9 defines "verifier failure" as "a success message earns reward even though the wrong record changed in the backend", i.e. a _false positive_ from the verifier. In the hackable regime the verifier is exactly right (`check_success` still reports failure) and the _reward function_ pays for a click; that is a mis-specified reward, not a verifier failure. The later cross-reference to Chapter 25.1 ("Why Higher Reward Can Make the Task Worse") is the accurate one; consider dropping the Step 9 label or rephrasing it as "what Step 9 asks you to diagnose -- a metric that moves while the task does not".

5. `docs/chapter22_computer_use/lab.md` (Background) — "The curriculum (Step 6) ramps task difficulty as rolling success crosses 50%, inside the 30-70% 'possible but not yet mastered' band" — Chapter 22 Step 6 uses the 0.3 <= P(success) <= 0.7 interval to _filter which tasks to sample_ (a MobileRL-style curriculum sampler), not as a promotion threshold for a sequence of difficulty levels; the lab's rule (promote the level when the rolling 200-episode success reaches 50%) borrows the wording but is a different mechanism. Chapter 22 also states that the 30-70% interval is "an experimental teaching setting, not a threshold prescribed by the MobileRL paper", so the page's mapping is defensible, but a reader may take it for the chapter's algorithm.

6. `docs/chapter22_computer_use/lab.md` (Setup) — "Outputs per run: `metrics_<mode>.csv` ..., `eval_<mode>.csv` ..., `summary.json`, and `training_curves.png`" — `training_curves.png` is written only when more than one mode is trained (`if len(modes) > 1: plot_curves(...)`), so a single-mode invocation (e.g. the `--mode shaped --episodes 2000` example two lines above) produces no PNG. Minor, but the sentence promises an output that the documented single-mode command does not create.

7. `docs/chapter22_computer_use/lab.md` (Setup) — "Full comparison (~4 min on CPU, deterministic under --seed)" — the run reproduced here took 268 s, and the seed fixes the episode seeds, the network init and the sampling, but the trajectory also depends on the torch version, the BLAS kernel and the thread count (the script sets `torch.set_num_threads(1)` on the CPU path). The reported table reproduced exactly on this machine, which is reassuring, but "deterministic" is stronger than one machine can establish; the report itself notes one unreproducible SIGSEGV at process exit. Consider "reproducible under --seed on the same machine".

8. `code/chapter22_computer_use/gui_env.py` (Task / verifier) — a box target of `False` ("uncheck X") is satisfied from the initial state, so the corresponding sub-goal (a) never pays progress reward and (b) is _broken_ by a random click on that box, which is an unusual task specification for a GUI form ("leave this box alone"). The page's "Five correct actions among 28" framing (What to look for) also silently assumes both box targets are "check", which holds in only 25% of episodes. The mechanics are self-consistent and the verifier is correct; consider noting the "uncheck" case explicitly in the walkthrough so the reader can reproduce the progress-reward arithmetic (2, 3 or 4 payable sub-goals per episode).

## Verdict

This is a well-executed and unusually honest lab: the environment, the REINFORCE-with-baseline implementation and the success-replay filter are correct, the 22 unit tests pass, and I reproduced the reported run end-to-end and got the summary table _exactly_ as printed in both `lab.md` and the code README, with the narrative numbers (16 sparse successes, promotions at 1000/4000/7500, 0.366 final curriculum success, hackable submit share 0.09 -> 0.98) all confirmed from the CSVs -- so there is no fabrication and no over-precise claim in the results section. The defects are all in the description layer: the central description of the deliberate reward flaw ("every submit click, right or wrong") is false, since the code pays the 0.4 bonus only on _failed_ submits, and the same error is duplicated in the `gui_env.py` docstring and comment; the results table's "mean reward" column is the mean over the last 200 stochastic _training_ episodes while the header claims it is the greedy snapshot (for the hackable row the greedy value would be exactly 6.24, not 6.173); the level-0 "luck" rate is stated as 10-15% when it measures 8.2-8.8%; exercise 2 asks the reader to change a constant that cannot affect the regime it names; exercise 3 cites a "30-line BC probe in the report" that does not exist; and the new page was never added to the VitePress sidebar, so it is not navigable and its hand-invented "22.L" label is outside the book's numbering convention and invisible to the heading-sync script. Fixing items 1-4 and 6 would make this mergeable; the remaining points are wording and naming precision.
