# Review of appB-text

Scope reviewed: `docs/appendix_b_algorithms/` (all eight pages read in full at `w/appB-text`), `planning/reports/appB-text.md`, and `docs/.vitepress/config.mjs` (sidebar entries B.1–B.8). Base: `english-only...w/appB-text` (8 doc files + the report).

Every changed code block was executed with `.venv/bin/python` (torch 2.14 / numpy 2.5): the `unbiased=False` z-score vs `np.std` (`[1,2,3]` → ±1.2247 in both, and ±1.0 with the old Bessel default), `std(dim=1, keepdim=True, unbiased=False)`, `scatter(-1, …)` on 1-D and 2-D top-p (the old `scatter(1, …)` raises `IndexError: Dimension out of range`), `clamp_min(0)` cross-entropy vs `F.cross_entropy(..., ignore_index=-100)` (identical to 1e-7), `1 - dones.float()` for bool `dones` (`1 - bool_tensor` raises `NotImplementedError` in torch 2.14), the DAPO overlong-penalty schedule, and the KTO masked-assignment snippet (gradients flow correctly).

## Errors

1. `docs/appendix_b_algorithms/dapo.md` — "DAPO introduces a buffer: lengths inside `[max_len - buffer_len, max_len]` are not penalized, beyond `max_len - buffer_len` a linear deduction kicks in, capped at `-penalty_factor`" — **the sentence contradicts itself and contradicts the page's own code.** The two clauses describe different regions: the first says the whole buffer zone `[max_len − buffer_len, max_len]` is free, the second says the deduction starts *inside* it. The code (`soft_overlong_penalty`) and the DAPO report agree with the second clause: with `max_len=2000, buffer_len=500, penalty_factor=1.0` the page's own function returns `L=1500 → 0.0`, `L=1800 → −0.6`, `L=2000 → −1.0`, i.e. lengths **inside** the buffer zone already pay a linearly ramping deduction (0 at `max_len − buffer_len`, reaching `−penalty_factor` at `max_len`), and only lengths `≤ max_len − buffer_len` are unpenalized. — Suggested fix: "lengths up to `max_len − buffer_len` are not penalized; inside the buffer zone the deduction ramps linearly from 0 to `−penalty_factor` at `max_len`, and stays at `−penalty_factor` beyond that."

2. `docs/appendix_b_algorithms/dapo.md` (DAPO Total Loss sketch, comment added by this revision) — "ratio = exp(new_logp - old_logp)  # [B, T], advantages broadcast [B, G] -> [B, T]" — **the shape claim is wrong.** NumPy/PyTorch broadcasting of `[B, G]` against `[B, T]` requires `G == T` (or one of them being 1); here `G` is the group size (8, 16, …) and `T` the sequence length, so the two can never be broadcast against each other. The token-level loss needs the group dimension either folded into the batch (`[B*G, T]` log-probs with `[B*G, 1]` advantages, as verl does) or kept explicit (`[B, G, T]` log-probs with advantages expanded to `[B, G, 1]`). The previous version of the sketch carried no shape comment, so the revision introduced this claim. — Suggested fix: "ratio = exp(new_logp - old_logp)   # [B*G, T]; advantages [B*G, 1] (one per completion, constant over its tokens)".

3. `docs/appendix_b_algorithms/dpo-family.md` — "`log_ratio_w` / `log_ratio_l`: $\log\frac{\pi_\theta}{\pi_{ref}}$, the implicit reward per response (divided by $\beta$)" — **the implicit reward is the log-ratio *multiplied* by $\beta$, not divided by it.** The DPO paper defines $r_\theta(x,y)=\beta\log\frac{\pi_\theta(y|x)}{\pi_{ref}(y|x)}$, and this book derives the same thing twice: `docs/chapter14_dpo/dpo-objective-derivation.md` ("Step 3": $r(x,y)=\beta\log\frac{\pi^*(y|x)}{\pi_{ref}(y|x)}+\beta\log Z(x)$) and `docs/chapter14_dpo/dpo-theory-and-family.md` ("Implicit Reward": $r(x,y)=\beta\log\frac{\pi_\theta}{\pi_{ref}}$). The page's own formula then multiplies by $\beta$ again (`logits = beta * (log_ratio_w - log_ratio_l)`), so as written the page states the reward twice with opposite scalings. — Suggested fix: "the implicit reward per response is $\beta\log\frac{\pi_\theta}{\pi_{ref}}$ (multiply by $\beta$)".

4. `docs/appendix_b_algorithms/dpo-family.md` (KTO paragraph, sentence added by this revision) — "the original paper writes the same optimum with a $\lambda - \sigma(\cdot)$ value formulation" — **the two losses are not the same objective, so "the same optimum" is wrong.** With $z=\beta\log\frac{\pi_\theta}{\pi_{ref}}-z_{ref}$, the page's snippet has $\frac{d}{dz}[-\log\sigma(z)]=-\sigma(-z)$, while the paper's value form has $\frac{d}{dz}[\lambda-\sigma(z)]=-\sigma(z)(1-\sigma(z))$: different curvature, hence a different effective weighting of samples in the same batch. The difference is largest exactly where the page's prose matters: for an undesirable sample the value form saturates at $\lambda_U$ once $z\ll 0$, while $-\log\sigma$ keeps growing like $|z|$ (linearly in the log-ratio gap), so the logistic version keeps punishing hopeless samples long after the value formulation has stopped caring. Only the *direction* of the optimum (push the log-ratio up for desirable, down for undesirable) is shared. — Suggested fix: say the snippet is a logistic surrogate of the paper's value form and state the saturation difference, e.g. "the paper's value form saturates at $\lambda_U$; this logistic version keeps a logarithmic penalty on hopeless samples".

5. `docs/appendix_b_algorithms/top-k-top-p.md` — Comparison table, "Selection rule | keep exactly k" — **the page's own two implementations do not keep exactly $k$.** Both keep every logit that *ties* with the $k$-th largest: NumPy `np.where(logits >= threshold, logits, -np.inf)` and PyTorch `logits.masked_fill(logits < threshold, -inf)` (the revision's report lists "top-k tie behavior" as a checked non-issue, but the prose/code mismatch was left in place). With a saturated or heavily quantized logit vector the surviving set can be much larger than $k$, which is exactly the regime where top-k is supposed to bound the tail. — Suggested fix: "keep the top k logits (plus any logits tied with the k-th largest)".

## Doubts

1. `docs/appendix_b_algorithms/dapo.md` — the revision re-labelled step 5 of the "DAPO Total Loss" sketch from "# 5. KL penalty (same as GRPO)" to "# 5. KL penalty (optional, as in GRPO)". To my recollection the DAPO report *removes* the GRPO-style KL term from its objective (the KL constraint is one of the things the paper argues is unnecessary once clip-higher / dynamic sampling / token-level loss are in place, and verl's DAPO recipe runs with `kl_loss_coef = 0`). If so, listing a KL term as step 5 of "the DAPO loss" — even as "optional" — misrepresents the algorithm this page is a cheatsheet for. — Please check the DAPO report's objective and, if the KL term is indeed dropped, write "DAPO drops the GRPO KL term (shown here only for comparison)" or remove the step.

2. `docs/appendix_b_algorithms/dpo-family.md` — "The form below is the TRL-style logistic implementation (`-log_sigmoid`)". As far as I remember, TRL's `KTOTrainer` implements the paper's *value* form, i.e. `1 - sigmoid(beta * (chosen_logratios - z_ref))` and `1 - sigmoid(beta * (z_ref - rejected_logratios))` (that is $\lambda_y=1$), not `-log_sigmoid`; if that is right, the new sentence inverts the relationship (TRL = the paper's form, the page = the logistic surrogate), and the reader is told the wrong source for the snippet. — Please verify against the TRL source and correct the attribution.

3. `docs/appendix_b_algorithms/grpo-rlvr.md` — the revision switched the PyTorch normalizer to `unbiased=False` so that it matches the page's NumPy snippet. That internal consistency is right, but as far as I remember the common production implementations (verl's `compute_grpo_outcome_advantage`, OpenRLHF) use `torch.std`'s default, i.e. the Bessel-corrected (denominator $G-1$) value, so the cheatsheet now differs from the code most readers will actually meet; for $G=8$ the two normalizers differ by a factor $\sqrt{8/7}\approx 1.069$ in the advantage scale. — Consider stating both conventions and noting which the frameworks use, instead of silently picking one.

4. Cross-page (not introduced here, but visible from the appendix): `docs/chapter15_grpo/deepseek-dapo.md` describes DAPO's dynamic sampling as "Keep only prompts whose accuracy is below the threshold" (0.95) with a code sketch that filters on accuracy, while Appendix B.5 states the criterion is "within-group reward variance is 0" (and this revision hardened the appendix's wording to exactly that). The two filters are different: the accuracy rule also discards *mixed* groups (e.g. 7/8 correct), which is precisely the case DAPO keeps. — If Chapter 15 is out of scope for this pass, at least add a pointer from B.5 to 15.2 so the reader does not see two different definitions of the same technique.

5. `docs/appendix_b_algorithms/dpo-family.md` — "`gamma` ($\gamma$): target margin, a learnable-style threshold for 'how much higher the good response must beat the bad'". In the SimPO paper $\gamma$ is a fixed hyperparameter (the target reward margin $\gamma/\beta$, commonly set to a constant such as $\beta/2$); the paper discusses a learnable variant only as an ablation it does not use. Calling it "learnable-style" will make readers think it is trained. — Suggested fix: "target reward margin, a fixed hyperparameter (not trained)".

6. `docs/appendix_b_algorithms/dapo.md` — the acronym is expanded as "Decoupled Clip and Dynamic sAmpling Policy Optimization" (odd capital *S*, as in the paper) while `docs/chapter15_grpo/deepseek-dapo.md` writes "Decoupled Clip and Dynamic Sampling Policy Optimization". Trivial, but pick one spelling for the expansion so the two chapters do not look like different algorithms.

## Verdict

This is a disciplined, mostly correct revision: I re-executed every changed snippet and each fix does what the report says (the `unbiased=False` normalization really does reproduce `np.std`; `scatter(-1, …)` really is the right call for 1-D and 2-D inputs; `clamp_min(0)` really does make the manual cross-entropy equal `F.cross_entropy`; `1 - bool_tensor` really does raise in current PyTorch, so the GAE `dones` fix is a genuine bug fix; the LLaMA-2 GQA correction and the DPO/SFT detach notes are accurate; and the RLVR "no reward hacking risk" sentence was correctly softened). The problems are not in the code but in the prose that surrounds it. Two newly written statements are wrong: the DAPO sketch's `[B, G] -> [B, T]` broadcast claim, and the KTO sentence claiming the logistic and value formulations share "the same optimum" (they are different objectives with different saturation). Two pre-existing statements the writer should have caught are also wrong: the DAPO overlong-penalty paragraph contradicts its own code, and the DPO "implicit reward (divided by β)" contradicts both the DPO paper and Chapter 14 of this book. The top-k "keep exactly k" claim also contradicts the page's implementations. The remaining doubts are attribution checks (whether TRL uses `-log_sigmoid`, whether DAPO drops the KL term, which std convention production code uses) plus one cross-page inconsistency with Chapter 15's description of DAPO's dynamic sampling. Fixing errors 1–4 and clarifying 5 would make the appendix mergeable.
