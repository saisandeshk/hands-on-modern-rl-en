The "N.R" label also contradicts the book's own convention — every other chapter's summary page is the next sequential number (`1.4`, `2.4`, `3.4`, `4.4`, `5.6`, `7.8`, `10.4 Summary and Exercises` in the sidebar), and no other page in `docs/` uses a letter suffix in its H1. — Suggested fix: add `{ text: '21.3 Summary and Exercises', link: '/chapter21_deep_research/review' }` to the Chapter 21 sidebar block and change the front-matter `title:` and the H1 to `21.3` (then run `npm run fix:headings`).

2. `docs/chapter21_deep_research/browser-rl-harness.md` (Step 3, lines 619–630) — "var_r = sum((r - mean_r) ** 2 for r in rewards) / len(rewards)" with the comment "# Clipped policy update over all group members (see Chapter 15):" — this is the **population\*\* standard deviation (denominator $G$), but Chapter 15 (`docs/chapter15_grpo/grpo-practice-and-mechanism.md`, line 487) explicitly fixes the opposite convention: "The example follows the default definition of PyTorch `torch.std` and uses Bessel's correction", and its worked example is consistent with that. Recomputation on the group implied by the page's own printed statistics (six rewards $[1.5, 0.0, 1.5, 0.0, 1.0, 1.0]$, the only combination consistent with "mean = 0.83"): mean $=0.833$, population std $=0.624$ (advantages $+1.07$, $-1.34$), sample std $=0.683$ (advantages $+0.976$, $-1.22$) — the page prints "std = 0.69", "A_1 = +0.97", "A_2 = -1.20", i.e. the Bessel-corrected value. So the new snippet is not "the same group-normalized update introduced in Chapter 15": it rescales every advantage by $\sqrt{G/(G-1)}$ (1.155× at $G=4$). The two chapters also disagree on what happens for a degenerate group: Ch15's code sets the advantage to 0 via `torch.where(group_std < eps, 0, advantages)`, while the ch21 snippet only gets 0 by accident ($0/10^{-8}$). — Suggested fix: use `len(rewards) - 1` (or `statistics.stdev`) so the snippet matches Ch15, or state explicitly in the comment that this page uses the population std and that it differs from Ch15 by $\sqrt{G/(G-1)}$.

3. `docs/chapter21_deep_research/review.md` (Exercise 3, lines 99–107) — "(a) Compute the group mean and (population) standard deviation." / "Variance $= ... = 1/4 = 0.25$, so std $= 0.5$" / "$A = ([0,0,1,1]-0.5)/0.5 = [-1,-1,+1,+1]$" — the printed answer follows the population std, so it disagrees with the convention the same page inherits from Chapter 15 (Bessel-corrected): $\mathrm{std}([0,0,1,1])=\sqrt{(0.25\cdot4)/3}=\sqrt{1/3}\approx0.577$ and $A\approx[-0.866,-0.866,+0.866,+0.866]$. The exercise is advertised as the companion to the Ch15 update ("GRPO group-relative advantage for rewards $r_1,\dots,r_G$"), so a reader who checks the numbers against Chapter 15 will find two different values for the same quantity. — Suggested fix: either use the sample std (std $\approx0.577$, $A\approx\pm0.866$) to match Ch15, or keep the population std and add one line: "This page uses the population standard deviation; Chapter 15 uses Bessel's correction, so the advantages there are $\sqrt{G/(G-1)}$ times larger."

6. `docs/chapter21_deep_research/browser-rl-harness.md` (lines 1219–1221 vs. 1137–1138) — "next_observation, reward, done, truncated = env.step(action)" / "if done or truncated:" — the wrapper that this rollout calls is defined 80 lines earlier with the contract `"""Return next_observation, reward, done, and diagnostic info."""`, i.e. the 4th value is a dict, not a boolean flag. Under the documented contract `if done or truncated:` is truthy for any non-empty info dict, so every trajectory would break after its first step; and if `info` is empty the flag is silently ignored. The Gymnasium-style contract would return five values (`obs, reward, terminated, truncated, info`). — Suggested fix: make `BrowserEnv.step` return `(next_observation, reward, done, truncated)` (or the 5-tuple) and update its docstring to match the caller.

7. `docs/chapter21_deep_research/review.md` (Exercise 8 solution, lines 195–217) — "class TinyResearchEnvRetry(TinyResearchEnv): def **init**(...): ... self.\_cache = {}" — `reset()` is not overridden, so the idempotency cache survives episode boundaries and a key reused in a later task returns the _previous_ task's observation. I ran the printed code against the page's `TinyResearchEnv` (lines 72–97 of 21.1) and reproduced it: after `env.reset("q2")`, `env.step({"name": "search", "query": "y", "idempotency_key": "k1"})` returns `{'hits': ['x']}` — the first episode's result — and the backend call counter stays at 1 (the search is never executed). This directly contradicts the section's own requirements ("reset browser profile state between tasks", "deterministically replayed") and makes the harness unsafe for training batches, where keys are usually reused across prompts. — Suggested fix: override `reset()` in the subclass to clear `self._cache` (or namespace the keys by an episode id) and add one line to the exercise text saying that the cache must be cleared on reset.

8. `docs/chapter21_deep_research/review.md` (Exercise 8 solution, lines 214–217) — "result = super().step(action) / if key is not None: self.\_cache[key] = result" together with the duplicate branch "return observation, 0.0, False, ..." — the cache stores _every_ keyed action, including the terminal `answer` action whose `super().step` result carries the verifier's score and `done=True`. A repeat of that key then returns the cached observation with reward 0.0 and `done=False`. Running the code: the first `answer` returns `({'status': 'submitted'}, 1.0, True, False)` and the retry returns `({'status': 'submitted'}, 0.0, False, False)` — the verifier's 1.0 is discarded and the episode never terminates, so a policy that re-submits with the same key is silently scored as a failure. The exercise statement scopes the key to tool actions ("Every tool action may carry an `idempotency_key`"), and `answer` is not a tool action. — Suggested fix: cache only `search`/`open` actions, or replay the cached `(reward, done)` for a repeated terminal action instead of `0.0, False`.

## Doubts

1. `docs/chapter21_deep_research/browser-rl-harness.md` (line 1259) — "Practical systems cap staleness (for example, discarding trajectories more than one or two versions old) because the clipped GRPO update only tolerates small policy drift." — clipping bounds how much a single token's objective can move when the importance ratio is large, but it does not remove the off-policy bias of stale rollouts (the ratios themselves are estimated from a policy that is no longer current, and the baseline is stale). The usual reason for capping staleness is biased/unreliable importance ratios rather than "the clip". Consider rewording: "because trajectories from an older policy are off-policy data whose importance ratios become unreliable".

2. `docs/chapter21_deep_research/deep-research-eval.md` (line 121) — "which is exactly why [Section 21.2 cost accounting](#layer-4-cost-and-reliability) must accompany any accuracy claim" — the anchor target is "Layer 4: Cost and Reliability", which is a subsection of the page the reader is already on (21.2). Labelling it "Section 21.2" reads like a link to another page, and 21.2's subsections are not numbered 21.2.x anywhere in the book. Suggest "[the cost layer](#layer-4-cost-and-reliability)".

3. `docs/chapter21_deep_research/deep-research-eval.md` (lines 123 and 125) — the heading says "### xbench-DeepSearch (Tsinghua University, 2025)" while the body says "released by Tsinghua University and the University of Hong Kong in 2025". The report itself lists the xbench attribution as unverified; please settle on one form and make both lines agree.

4. `docs/chapter21_deep_research/deep-research-eval.md` (line 332) — "[R1-Searcher](https://github.com/RUCAIBox/R1-Searcher) uses two-stage outcome-supervised RL" — as far as I can tell, R1-Searcher's second stage is supervised fine-tuning on the trajectories collected during the RL exploration stage, not a second RL stage, so "two-stage outcome-supervised RL" may mislabel the method. Worth checking against the R1-Searcher paper/README before shipping.

5. `docs/chapter21_deep_research/browser-rl-harness.md` (line 186 vs. the Search-R1 comparison table) — the softened Tongyi sentence now says only "a mid-scale mixture-of-experts model", while the same page still says "Tongyi 30B" and "Tongyi needs large cluster" in the comparison table and "30B+ models" in the "Advanced Directions" list. The removed figures (30.5B total / 3.3B active) correspond to the released Tongyi-DeepResearch-30B-A3B checkpoint, so they may not have needed removing; at minimum the page should keep one consistent description of the model size.

6. `docs/chapter21_deep_research/review.md` (Exercise 5, lines 130–140) — the displayed split `$\sum_{t\in\mathcal{M}}\nabla_\theta\log\pi_\theta(\cdot) + \sum_{t\in\mathcal{E}}\nabla_\theta\log\pi_\theta(\cdot)$` drops the conditioning arguments, and the solution does not note the subtlety that a model token generated _after_ an environment token is still conditioned on that token: masking removes the environment tokens' own log-probability term, but the policy gradient of the later model tokens still depends on the retrieved text. One clarifying sentence would prevent the common misreading that retrieved-token masking makes the multi-turn objective unbiased.

7. `docs/chapter21_deep_research/review.md` (Common pitfalls #2, line 51) — "**Collapsing four layers into one number.**" while 21.2's protocol section says "Compute answer, citation, process, cost, and reliability metrics separately" (five components). If reliability is a fifth metric rather than part of the cost layer, the wording should be reconciled.

## Verdict

The revision fixes several real problems and most of its new material is technically sound: the BrowseComp attribution (OpenAI) and GAIA dating (2023, Meta/Hugging Face/AutoGPT) are correct, deleting the fabricated BrowseComp leaderboard is right, replacing the DPO-style best/worst update with a genuine group-relative GRPO update is the single most valuable change, the `parallel_rollout` snippet now calls the wrapper synchronously and defines `max_steps` instead of an undefined `MAX_STEPS`, the duplication of the Tongyi figure is gone, and every arithmetic claim I re-checked holds (3/8 = 0.375 redundancy, 14/20 = 0.7 budget success, $0.99^{29}\approx0.747$, $0.9^{29}\approx0.047$, GRPO advantages $[-1,-1,1,1]$ under the population std, 256/90 ≈ 2.8 traj/s versus a verifier capacity of 8 traj/s that drops to 2 traj/s — i.e. the bottleneck — when the judge slows 4×). The serious problems are integration and verification: the new `review.md` page is not in the sidebar despite the report claiming it is (so it is unreachable and its "21.R" number contradicts the book's `N.M` convention), the two GRPO snippets contradict Chapter 15's explicitly stated Bessel-corrected standard deviation, the Exercise 8 code has two defects I reproduced by running it (the idempotency cache leaks across episodes, and caching the terminal `answer` action zeroes the verifier score and prevents termination), the new "Rollout Scheduling" section contains two counting slips ("four kinds of state" with three listed, "four rates" of which three are rates), the rollout code now treats the wrapper's documented "diagnostic info" return value as a boolean truncation flag, and the report justifies removing a correct BrowseComp example with a false claim about the 1998 quarter-final. Fixing Errors 1–8 and correcting the report would make this mergeable; the remaining doubts are wording-level.
