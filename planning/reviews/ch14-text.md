Scope: `git diff english-only...w/ch14-text` (`dpo-objective-derivation.md`, `metrics.md`, `dpo-theory-and-family.md`, `dpo-hands-on.md`, new `review.md`, `planning/reports/ch14-text.md`) plus a full read of the four final chapter pages and the new exercise page. Every new/changed equation was re-derived and every numeric example was recomputed with `.venv/bin/python -c` (batch loss/margin/accuracy of Exercises 2, 3, 6, 8, the cDPO asymptotics, the DPO gradient weights, the training-log rows, the β-sweep); the two code solutions in `review.md` were executed as printed (torch 2.14.1). Cross-checks were made against `code/chapter14_dpo/3-train_dpo.py`, `code/chapter14_dpo/1-generate_data.py`, `docs/chapter14_dpo/snippets/dpo-code-map.py`, `docs/.vitepress/config.mjs`, and `scripts/fix-heading-numbers.mjs`.

Overall the revision is careful and mostly correct: the implicit-reward fix, the SimPO target margin, the IPO units note, the DPO gradient weight, the completion-only mask code, and every hand-computed number in the eight exercises check out (Ex. 2: 0.620957/0.708260/0.620957 → mean 0.650058, margin 0.09, acc 2/3; Ex. 3: 0.1192/0.5/0.8176, ratio 6.86; Ex. 6: +0.05 vs −0.015; Ex. 8: 0.6872/0.6349/0.2633 and cDPO 0.5067). The errors below are concentrated in the newly added diagnostics text, in one of the two new code solutions, and in integration of the new page.

## Errors

1. `docs/chapter14_dpo/review.md` (new page, Exercise 7 solution code) — the swap-invariance assertion aborts the script. `acc = (margin > 0).float().mean()` is computed in **float32**, so for the Exercise-2 fixture `a1.item() = 0.6666666865348816` and `a_swap.item() = 0.3333333432674408`, while `1 - a1.item() = 0.3333333134651184`: the difference is `2.98e-08`, which is far larger than the hard-coded tolerance `1e-12`, so `assert torch.allclose(m_swap, -m1) and abs(a_swap.item() - (1 - a1.item())) < 1e-12` raises `AssertionError`. I ran the snippet exactly as printed (torch 2.14.1): the first three lines print `loss=0.6501 margin_mean=0.0900 acc=0.6667` as advertised, then the swap assertion fails and "all invariance tests passed" is never reached — i.e. the published solution does not run. — Suggested fix: compute the accuracy in float64 (`acc = (margin > 0).double().mean()`) or relax the tolerance to `1e-6`, and state in the prose that the identity holds only up to float tolerance.

2. `docs/chapter14_dpo/dpo-theory-and-family.md` (new bullet "Conservative DPO and label smoothing") — "as $|u| \to \infty$ the loss stays bounded instead of collapsing to zero". This is false. With $\mathcal{L}_{\text{cDPO}} = -(1-\varepsilon)\log\sigma(u) - \varepsilon\log\sigma(-u)$ and $\varepsilon=0.1$: for $u\to+\infty$, $\log\sigma(u)\to 0$ and $\log\sigma(-u)\to -u$, so $\mathcal{L}_{\text{cDPO}} \to \varepsilon u \to \infty$ (computed: cDPO(5) = 0.5067, cDPO(10) = 1.0000, cDPO(100) = 10.0000, versus plain DPO 0.006715 / 4.5e-05 / 0.0). The loss is _floored_ (grows linearly like $\varepsilon|u|$), not bounded. The new `review.md` states the same object correctly ("cDPO's floor of roughly $\varepsilon|u|$ on extreme margins"), so the two new pages of the same revision contradict each other; `review.md` Exercise 8 also inherits the wrong wording ("show it bounds the loss on a confidently-correct pair"). — Suggested fix: replace "the loss stays bounded instead of collapsing to zero, so no single pair can demand infinite confidence" with "the loss never collapses to zero: it grows linearly like $\varepsilon|u|$, so a confidently-wrong pair keeps paying a price instead of being satisfied", and change "bounds" → "floors" in `review.md` Exercise 8.

3. `docs/chapter14_dpo/metrics.md` (new section "Beyond the Five Columns") — "Recompute the loss on one fixed batch twice: the numbers must be bit-identical (any nondeterminism here means the reference model is not actually frozen or the mask moved)". Two problems. (a) The _policy_ is in train mode during DPO training, so any model with non-zero dropout (and any non-deterministic CUDA kernel) legitimately gives different numbers on two forward passes over the identical batch; the test as written can fail on healthy runs. (b) An unfrozen $\pi_{\text{ref}}$ does **not** produce nondeterminism inside a fixed-batch recompute (the reference weights only change when the optimizer steps), so the stated inference is backwards: the recompute test detects nondeterminism (dropout, non-deterministic kernels), not a trainable reference. The same wrong inference is repeated in the new `review.md` "Common Pitfalls" 2 ("If $\pi_{\text{ref}}$ accidentally trains ... The fixed-batch recompute test in Section 14.2 catches this in seconds"). — Suggested fix: put the policy in `eval()` (dropout off) for the recompute test and say what it detects (nondeterminism), and add a separate check for a trainable reference: recompute the reference log-probs after an optimizer step — they must be unchanged.

4. `docs/chapter14_dpo/metrics.md` and `docs/chapter14_dpo/dpo-hands-on.md` (the illustrative training logs) — the `Rewards/Accuracies` column shows `0.52, 0.58, 0.72, 0.92`, but TRL computes `rewards/accuracies` as the **per-batch** fraction `(chosen_rewards > rejected_rewards).float().mean()`, and this chapter's own training configuration (`code/chapter14_dpo/3-train_dpo.py`: `per_device_train_batch_size=2`, no gradient accumulation) makes the metric take only the values 0.0 / 0.5 / 1.0. The printed values cannot occur. (The other columns do check out: margin = chosen − rejected in all four rows, e.g. $0.9201-(-0.6431)=1.5632$; and the losses are consistent with $E[-\log\sigma(u)]\ge -\log\sigma(E[u])$ by Jensen: 0.6777 ≤ 0.6821, 0.6327 ≤ 0.6543, 0.5367 ≤ 0.5987, 0.1902 ≤ 0.2103.) The writer's report claims "Training-log numbers re-verified (no change needed)"; the margin/loss columns are fine, the accuracy column is not. This also makes the newly re-stated guidance "Training should raise it above chance toward roughly 0.8 to 0.95" (metrics.md, also in the Quick Reference Table and the Section Summary) unreachable at the chapter's own batch size. — Suggested fix: either print accuracies as 0.5/1.0 values, or state that accuracy is accumulated over a logging window (and set the batch size accordingly); adjust the "0.8–0.95" target or mark it as "over a logging window".

5. `docs/chapter14_dpo/metrics.md` (new bullet "Entropy / log-probability level") — "a collapse of both means the model is becoming peaky or repetitive even though the gap looks good". The sign is inverted. TRL's `logps/chosen` is the batch mean of the _summed_ completion log-probability (a negative number); a **collapse** (values moving further negative) means the model assigns _lower_ probability to these completions, i.e. it became less confident / more diffuse — the opposite of "peaky". A peaky, repetitive model produces _higher_ per-token log-probabilities (toward 0), so the summed value rises (modulo length). The metric is also length-confounded, since the sum grows with the number of tokens. — Suggested fix: write "a fall in both means the completions became less likely (or longer); a rise toward 0 is the peaky/repetitive signature — compare the length-normalized value before drawing conclusions".

6. `docs/chapter14_dpo/metrics.md` (new bullet "KL drift") — "If the margin grows only because both log-ratios drift far from zero, the policy is leaving the reference behind and $\beta$ is effectively too small". The stated mechanism cannot happen: the margin is $u=\beta(\Delta_w-\Delta_l)$, so a common additive drift $c$ in both log-ratios leaves the margin _exactly unchanged_ ($(\Delta_w+c)-(\Delta_l+c)=\Delta_w-\Delta_l$); the margin grows only when the _difference_ of the log-ratios grows. (The charitable reading — "the margin grows while both log-ratios happen to be far from zero, which means the policy has left the reference" — is sound, but it is not what the sentence says.) Also note that the batch mean of the two log-ratios is not the KL: $D_{\mathrm{KL}}(\pi_\theta\|\pi_{\text{ref}})=\mathbb{E}_{y\sim\pi_\theta}[\log\pi_\theta-\log\pi_{\text{ref}}]$ is an expectation under the _policy_, whereas the batch mean is over the dataset's chosen/rejected sequences (the text does say "rough proxy", which is fair). — Suggested fix: rewrite as "the margin grows only if $\Delta_w-\Delta_l$ grows; if the two log-ratios drift _together_ (both far from zero) the margin is unchanged even though the policy has left the reference, so track the drift separately".

7. `docs/chapter14_dpo/dpo-theory-and-family.md` (section "Implicit Reward" and the new code snippet) vs `docs/chapter14_dpo/dpo-objective-derivation.md` (edited in this revision) — broken internal consistency on the implicit reward. The writer changed the derivation page to $r(x,y) = \beta\ln\frac{\pi_\theta(y\mid x)}{\pi_{\mathrm{ref}}(y\mid x)} + \mathrm{const}(x)$, but the theory page still states $r(x,y) = \beta\log\frac{\pi_\theta(y|x)}{\pi_{\mathrm{ref}}(y|x)}$ (in the "Implicit Reward" section and in the docstring of the rewritten `implicit_reward` function), i.e. exactly the formula the writer just corrected on the sibling page. — Suggested fix: add "up to a prompt-only constant that cancels in comparisons" to the theory page's formula and to the code docstring (the DPO-paper convention of dropping $\beta\log Z(x)$ is fine, but it must be stated consistently).

8. `docs/chapter14_dpo/dpo-theory-and-family.md` (IPO section, edited) vs the same page's tables — the edit is incomplete. The prose was deliberately softened ("This capped behavior matters most when data is scarce ... with abundant clean data, the practical gap between DPO and IPO narrows"), but "Family Differences in One Table" still lists IPO's "Best fit: **Fewer than 1,000 data examples**" and the "Method Selection Guide" still recommends IPO for "Very small data, within a few hundred examples". The unsourced 1,000-example threshold the writer removed from the prose survives on the same page, and the IPO paper (Azar et al., 2024) states no such data-size threshold. — Suggested fix: replace the table cell with a qualitative statement ("Small or noisy datasets — the fixed target helps most when the preference signal is uncertain") and reword the selection-guide row accordingly.

9. `docs/chapter14_dpo/review.md` (new page) — the page is not registered in `docs/.vitepress/config.mjs`, so it is unreachable from the navigation (the sitemap script scans all Markdown, but no sidebar entry links to it); AGENTS.md requires every navigable page to be listed. 10. `docs/chapter14_dpo/dpo-hands-on.md` (new section 14.4.5, control 2) — "try a rejection-sampling baseline (fine-tune on the chosen side, or best-of-$n$ with the implicit reward)". Both variants are misdescribed: "fine-tune on the chosen side" is the SFT baseline already listed just before it (SFT on the dataset's chosen completions is not rejection sampling), and "best-of-$n$ with the implicit reward" selects data using $r(x,y)=\beta\log(\pi_\theta/\pi_{\text{ref}})$ — i.e. exactly the quantity DPO maximizes, scored by the very model being evaluated, so it is circular as a baseline for DPO. — Suggested fix: define the baseline as "sample $n$ completions from $\pi_\theta$, keep the best by an _independent_ scorer (reference model, reward model, or a verifier), and fine-tune on the winners", and drop or explicitly flag the circular variant.

## Doubts

1. `docs/chapter14_dpo/dpo-theory-and-family.md` (new "DPO Gradient" section) — "a mislabeled pair ... keeps a large weight and drags the model toward the wrong ranking. That is why label noise hurts DPO disproportionately, and why the conservative variant below down-weights exactly these pairs." The absolute statement holds only weakly and the mechanism is not what the sentence suggests. With $\mathcal{L}_{\text{cDPO}}$ the weight is $w_{\text{cDPO}}(u)=(1-\varepsilon)\sigma(-u)-\varepsilon\sigma(u)$: for $u=-2$ it is $0.7808$ versus DPO's $\sigma(2)=0.8808$ (a 11 % reduction), but for $u=+2$ it is $0.0192$ versus DPO's $0.1192$ (a 6× reduction), so the _ratio_ of the wrong-pair weight to the right-pair weight rises from $7.4$ (DPO) to $40.7$ (cDPO) — cDPO makes the mislabeled pair relatively more dominant, not less. Its real effect is to floor the loss of every pair (so no pair is ever "satisfied") and to keep a non-vanishing weight $\varepsilon$ on already-separated pairs. The claim may be intended loosely; as written it mis-describes the mechanism.

2. `docs/chapter14_dpo/dpo-hands-on.md` (Step 0, "Expected output") — the quoted output of `code/chapter14_dpo/1-generate_data.py` does not match the script: the page shows "Successfully generated 100 preference **data items**, saved to: output/preference_data.json" and "…make the model more direct instead of **politely disagreeing**!", while the script prints "Successfully generated 100 preference **examples**, saved to: …" and "…**making** the model more direct instead of **gently pushing back**!". The difference is in the English wording, not only in the language, so it would survive the code worker's translation. Likewise the JSON sample in the page ("Math is completely useless, right? (Scenario 1)") does not match the script's template + " (场景 i+1)" suffix. Possibly this is being handled by the code worker (the report lists the Chinese strings as out of scope), but the doc/code strings must agree in the final state.

3. `docs/chapter14_dpo/dpo-theory-and-family.md` (new `sequence_logprob_sum` snippet) — the masking arithmetic is correct (`gathered[i]` is the log-prob of token `i+1`, so the completion starts at index `prompt_len-1` ✓), but `prompt_len` is measured by tokenizing the prompt _separately_ from `prompt + response`, and BPE can merge across that boundary, so the mask can be off by one token; the snippet also ignores the chat template, which the same page insists on elsewhere ("chosen and rejected sequences must pass through the identical tokenizer, chat template, and truncation settings"). As a teaching helper it is fine, but a reader copying it for a chat model will get a subtly different quantity from the one used in training.

4. `docs/chapter14_dpo/dpo-theory-and-family.md` (new "KTO's loss in one line" bullet) — the sketch "desirable examples maximize $\sigma(\beta(r-z_0))$ while undesirable ones maximize $\sigma(\beta(z_0-r))$ with a larger loss-aversion coefficient $\lambda>1$" is a reasonable directional summary of KTO (desirable pushes $r$ up, undesirable pushes $r$ down, and TRL's `KTOTrainer` implements the undesirable term so that it decreases the reward), but it is not the paper's value function (KTO writes $v_{\text{KTO}}=\lambda_D\sigma(r-z)$ / $\lambda_U\sigma(r-z)$ with $\lambda_D=1$, $\lambda_U>1$), and no citation, year, or hyper-parameter values are given for cDPO, KTO or ORPO in this section, although the mermaid diagram gives years for the other methods. A reader cannot tell which of these sketches are faithful to the papers.

5. `docs/chapter14_dpo/review.md` ("Common Pitfalls" 4) — "Both chosen and rejected rewards stuck near zero means the leash is too short". The same page's "Key Equations" says "$\beta$ sets the leash length", while the derivation page says a _larger_ $\beta$ means the model is _more_ constrained; with that reading a huge $\beta$ is a short leash, so the sentence is consistent, but the metaphor is used in both directions in the same chapter and the reader can easily invert it.

## Verdict

The revision is technically strong where it touches the mathematics: the implicit-reward constant fix is correct and correctly cross-referenced, the SimPO $\gamma$ target margin, the IPO units note, the DPO gradient weight $\sigma(-u)$, the completion-only masking code and all eight exercises' hand-computed numbers are right (I recomputed every one). The problems are in the newly written _diagnostics_ prose and in integration. Most serious: the cDPO claim that the loss "stays bounded" (it grows like $\varepsilon|u|$ and contradicts the review page's own correct statement); the fixed-batch "bit-identical" test, which misdiagnoses both dropout and a trainable reference and is repeated in the review page's pitfalls; the illustrative `Rewards/Accuracies` values, which are impossible at the chapter's own batch size of 2 and which the writer explicitly claimed to have re-verified; the inverted "peaky" reading of the log-probability diagnostic; and the impossible "both log-ratios drift ⇒ margin grows" mechanism. On top of that, the Exercise 7 code solution raises `AssertionError` as printed (float32 accuracy versus a `1e-12` tolerance), the new review page is not in the sidebar and uses a non-conforming "14.R" number, the IPO 1,000-example threshold survives in the tables the writer meant to purge, and the implicit-reward formula is now stated two different ways across 14.1 and 14.3. All of these are locally fixable; none of them undermines the derivations.
