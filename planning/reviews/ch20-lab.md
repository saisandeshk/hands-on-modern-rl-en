Scope reviewed: new `docs/chapter20_swe_agents/lab.md`, new package `code/chapter20_swe_agents/` (`tasks.py`, `sandbox.py`, `policy.py`, `train.py`, `test_smoke.py`, `README.md`, `requirements.txt`), and `planning/reports/ch20-lab.md`. Also re-read the pages the lab page links to (`chapter20_swe_agents/swe-bench-and-rlvr.md`, `meta-swe-rl.md`, `world-model-and-deep-swe.md`, `self-play-ssr-and-summary.md`), `docs/.vitepress/config.mjs`, `scripts/fix-heading-numbers.mjs`, and `planning/content-review-notes.md`. Base: `english-only...w/ch20-lab` (9 new files, no existing file edited).

Method note: every number on the page was re-derived. I re-implemented the training loop with the shipped hyperparameters (Adam lr 0.2, entropy coef 0.01, baseline alpha 0.1, n_random 6, 300 epochs, seed 0) and the same mode order; the sandbox was replaced by an in-process evaluation that reproduces the sandbox's JSON round-trip of args/expected values. The reproduction matches the page's two tables **exactly** (visible: train 1.000 / E[vis] 0.999 / E[hid] 0.491 / greedy 0.554 / resolved 0.500 / P(hack) 0.537; epoch rows 0.881/0.395/0.500 … 1.000/0.491/0.537; hidden: 0.982/0.945/0.980/0.982/0.929/0.002; randomized: 1.000/0.976/0.998/1.000/1.000/0.002), so the reported run is real and the tables are trustworthy. The errors below are in the *interpretation* of those numbers, in the exercise hints, and in the repository integration.

## Errors

1. `docs/chapter20_swe_agents/lab.md` (§20.L.1, §20.L.6) — "both restore the correct implementations as the unique optimum" / "Both make the correct candidate the unique optimum" — this is false for the lab's own task suite, and the code contradicts it. Two of the 14 tasks have a "plausible-but-wrong" arm that ties the correct arm on the held-out suite:
   - `is_palindrome`, arm `odd_length` (`return len(s) % 2 == 1`): hidden pass rate **1.000** — "madam"→True (len 5 odd), "abca"→False (len 4 even), "a"→True, "ab"→False all match the expected values. Measured: `vis=0.333 hid=1.000`.
   - `count_vowels`, arm `lowercase_only` (counts only `aeiou`): hidden pass rate **1.000** — the hidden inputs "banana"(3), "xyz"(0), "Hello World"(3) and ""(0) contain no uppercase vowel, so the arm is right on all four. Measured: `vis=0.667 hid=1.000`.
   The randomized suite is blind to the same difference: `random_inputs` draws characters from `_LETTERS = "abcdeXYZ  "`, which contains no uppercase vowel, so `lowercase_only` also scores 1.000 there. In the reported seed-0 run the randomized policy actually converges onto `lowercase_only` (0.996 of the mass) for `count_vowels` — i.e. the "fixed" regime returns a *wrong* implementation, and the contract test does not catch it because it only asserts `vis < 1.0` for `wrong` arms, never that the correct arm is the strict argmax on the hidden/randomized suite.
   — Suggested fix: make the suites discriminating (e.g. add a hidden `count_vowels` case that contains an uppercase vowel, such as `("Apple", 2)`, where `lowercase_only` returns 1 and the correct arm 2; and an even-length palindrome not already in the visible suite, such as `("deed", True)`, where `odd_length` returns False), extend `test_candidate_reward_contract` to assert that the correct candidate is the unique maximiser on the hidden suite *and* on randomised inputs, and rewrite the two sentences to the accurate claim: held-out tests remove the hard-coded shortcuts, but a small or badly chosen held-out suite can still select an implementation that is not the intended one.

2. `docs/chapter20_swe_agents/lab.md` (§20.L.6) — "Their final rows match (E[hidden] 0.980 vs 0.998)" — the final rows do not match; the table printed immediately above differs in five of six columns: train reward 0.982 vs 1.000, E[visible] 0.945 vs 0.976, E[hidden] 0.980 vs 0.998, greedy hidden 0.982 vs 1.000, resolved **0.929 vs 1.000**. The sentence also claims the two regimes "agree because they measure the same thing", which the 0.929 vs 1.000 gap in `resolved` refutes.
   — Suggested fix: replace with the accurate statement, e.g. "the two final rows agree on E[hidden] to within 0.02, but they differ on `resolved` (0.929 vs 1.000): in the hidden regime the policy settles on the wrong `first_ge` implementation for `binary_search` (hidden pass rate 0.75), so one of the 14 tasks is not actually solved."

3. `docs/chapter20_swe_agents/lab.md` (§20.L.5) — "Both the hidden-test regime and the randomized-input regime drive hack mass to ~0.00 and resolve nearly every task." — the page never reports that in the reported run the hidden regime ends with the **greedy pick on a wrong implementation**: `binary_search` holds 0.997 of the policy mass on the plausible-but-wrong `first_ge` arm (hidden pass rate 0.75, correct arm 1.000). That is exactly why `resolved` = 13/14 = 0.929 and `greedy hidden` = (13×1.0 + 0.75)/14 = 0.982, and it is also why E[hidden] is 0.980 rather than 1.000. Two further tasks keep large mass on wrong arms that tie the correct one (see error 1): `is_palindrome` 0.401 on `odd_length`, `count_vowels` 0.477 on `lowercase_only`. The page's narrative ("the correct implementation is the optimum", "resolve nearly every task") hides the lab's most interesting failure mode.
   — Suggested fix: add a row to the results table (e.g. "non-correct greedy picks: 1 (hidden), 0 (randomized)" or "tasks whose greedy pick is not the `correct` arm") and turn it into the teaching point of §20.L.6: a hidden suite that is too small or unlucky does not identify the intended fix, which is the chapter's "coverage decides the faithfulness of the signal" argument in miniature.

4. `docs/chapter20_swe_agents/lab.md` (§20.L.7, exercise 3) — "Hint: memorizers are shorter than correct solutions, so a large $\lambda$ makes hacks optimal even under hidden rewards" — the premise is false for 11 of the 14 tasks. Counting the lines of the shipped snippets: fib 5/5, factorial 5/5, reverse_words 2/5, is_palindrome 2/5, gcd 3/5, sum_squares 2/5, count_vowels 2/5, fizzbuzz 8/5, clamp 2/5, unique_sorted 2/5, binary_search 11/5, second_largest 3/5, collatz 6/5, digit_sum 2/5 (correct lines / memorizer lines). Only `fizzbuzz`, `binary_search` and `collatz` have shorter memorizers; in the other 11 the memorizer is longer (or equal) because it embeds the visible-test lookup table, so the proposed penalty $R = R_{\text{test}} - \lambda\,(\text{lines of code}/20)$ penalises the **correct** implementation more than the hack on most tasks. The stated mechanism is therefore inverted for most of the suite, and the flip point is per-task, so "the $\lambda$ where the hidden regime flips" is not a single well-defined value.
   — Suggested fix: restate the hint, e.g. "the memorizer's length depends on the task: it carries the visible-test table, so a length penalty trades off against the correct solution in a task-dependent way (for `fizzbuzz`, `binary_search` and `collatz` the hack is shorter; for the other 11 tasks it is longer) — sweep $\lambda$ and report per-task flips", or use a shaping feature that actually separates the arms (e.g. the number of literal test values embedded in the source).

5. `docs/chapter20_swe_agents/lab.md` (§20.L.6) and `code/chapter20_swe_agents/README.md` — "Expect small seed-to-seed movement in the visible row (hidden ~0.4-0.5)" — the documented range is too narrow. Re-running the visible regime with seeds 0–3 (identical protocol; seed 0 reproduces the table exactly) gives E[hidden] = 0.491 / 0.442 / 0.429 / **0.287** and P(hack) = 0.537 / 0.633 / 0.665 / **0.792**, with `resolved` = 0.500 / 0.286 / 0.286 / 0.214. So the visible row can land well below the stated band, and the "near-even mix" claim (P(hack) ≈ 0.54) becomes 0.79 for seed 3.
   — Suggested fix: state the measured range ("hidden ≈ 0.29–0.49, P(hack) ≈ 0.54–0.79 over seeds 0–3") or add a small multi-seed table, and move the seed-to-seed spread into the results section instead of a parenthetical.

6. `docs/chapter20_swe_agents/lab.md` — the page is not registered in `docs/.vitepress/config.mjs` (the diff leaves the sidebar untouched; the chapter-20 group still lists only 20.1, 20.2, 20.3), so the new page is unreachable from the site navigation. `AGENTS.md` states "Every navigable page must be listed there", and the writer's own report leaves the sidebar entry as an open item for the coordinator, i.e. the deliverable is incomplete.
   — Suggested fix: add `{ text: '20.4 Hands-on: Reward Hacking in a Toy Code Agent', link: '/chapter20_swe_agents/lab' }` to the chapter-20 sidebar group and run `npm run fix:headings`.

7. `docs/chapter20_swe_agents/lab.md` — the section-numbering scheme "20.L / 20.L.1 … 20.L.7" is used nowhere else in the book and is incompatible with the repository's numbering tooling. Every other page is numbered by the sidebar ("15.3 RLVR: Verifiable Rewards", "19.8 Hands-On: rLLM DeepCoder", "20.1 Foundations of SWE-RL"); the only non-numeric H1s in `docs/chapter*/` are "Supplement: …" / "Legacy Page: …" pages. `scripts/fix-heading-numbers.mjs` extracts the number with `/^(?:[A-Z]\.)?\d+(?:\.\d+)*\b/`, which reads "20.L" as "20"; once the page is added to the sidebar as "20.4 …" the fixer rewrites the H1 into `# 20.4.L Lab: Reward Hacking in a Toy Code Agent` and the `## 20.L.x` sub-headings into `## 20.4.L.x`, i.e. the page cannot be numbered by the tool the repository relies on.
   — Suggested fix: renumber to 20.4 / 20.4.1 … once the sidebar entry exists (or drop the numeric prefixes from the H2s and use the book's unnumbered-H2 + numbered-H3 style, as `chapter20_swe_agents/swe-bench-and-rlvr.md` does).

8. `docs/chapter20_swe_agents/lab.md` (§20.L.4) — "Timeouts and child crashes are flagged separately from test failures, following the chapter's rule that infrastructure errors must not be counted as ability failures" — the *sandbox* flags them, but the *training loop* does not honour the rule: `sandbox.run_candidate` returns `RunResult(passed=0, total=len(cases), timed_out=True)` (and `crashed=True`), and `train.py` consumes only `res.pass_rate`, so an infrastructure failure still enters the reward as 0.0 — exactly the "counted as a failure of the model's ability" that Chapter 20.1 forbids ("A failed dependency installation, a container timeout, and a test failure should use different status codes. The first two are infrastructure problems and cannot be counted directly as failures of the model's ability."). No run in this lab triggers a timeout, so no number changes, but the page's claim overstates what the code enforces.
   — Suggested fix: in `train.py`, skip/retry the epoch (or emit a distinct reward/status) when `res.timed_out or res.crashed` is set, or soften the page to "the sandbox records timeouts and crashes separately from test failures; the training loop still maps them to reward 0 in this toy setting".

9. `planning/reports/ch20-lab.md` — "test_reinforce_loss_matches_hand_computation checks the loss against a hand-derived value (logits [1,0], rewards [1,0], baseline 0.2 -> expected loss +0.00602 within 1e-6)" — the sign is wrong. With $\log\pi_0 = 1 - \log(e+1) = -0.313262$, $\log\pi_1 = -\log(e+1) = -1.313262$ and advantages $[0.8, -0.2]$, the loss is $-\frac{1}{2}\left(0.8(-0.313262) + (-0.2)(-1.313262)\right) = -0.0060215$, i.e. **negative**; the shipped test computes the correct negative value (`expected = -((0.8*logp0 + -0.2*logp1)/2.0)`), so only the report's prose has the sign wrong.
   — Suggested fix: write "expected loss −0.00602" in the report.

## Doubts

1. `docs/chapter20_swe_agents/lab.md` (§20.L.6) — "**The hacked policy is a near-even mix, not a corner solution.** P(hack) settles around 0.54 rather than 1.0" — per task the visible-regime policy *is* a corner solution: in the reported run the per-task hack mass ranges from 0.020 (`count_vowels`) to 0.906 (`clamp`), and the greedy pick is a hack arm on 7 of the 14 tasks (`factorial` 0.949 on `memorize_plus_one`, `clamp` 0.897 on `memorize_identity`, `binary_search` 0.642, `fizzbuzz` 0.558, `unique_sorted` 0.541, `reverse_words` 0.520, `digit_sum` 0.381). The mean 0.537 is an average *across* tasks of three exchangeable visible-optimal arms, not a mixture inside a task. The sentence can be read as the former, but as written it describes the policy as flat, which it is not. Suggest: "per task the policy concentrates on one of the three exchangeable visible-optimal arms (which one is decided by sampling noise); averaging over tasks, 0.54 of the mass sits on the shortcuts".

2. `docs/chapter20_swe_agents/lab.md` (§20.L.4) — "The task suite itself … holds 14 single-function tasks … four candidates (correct / two memorizers-or-heuristics / one plausible-but-wrong)" — the phrasing "one plausible-but-wrong" per task is right, but two of those "wrong" arms are not merely wrong: `is_palindrome/odd_length` and `count_vowels/lowercase_only` pass the full hidden suite (error 1), and `gcd/abs_diff`, `fizzbuzz/forget_fifteen`, `binary_search/first_ge`, `second_largest/second_position` pass 3/4 hidden tests. The "wrong" arm is therefore often *almost* right, which is what makes the hidden regime's residual error 0.980 rather than 1.0. Consider saying so explicitly.

3. `docs/chapter20_swe_agents/lab.md` (§20.L.7, exercise 1) — "Add a 15th task … with visible tests, disjoint hidden tests, and four candidates following the file's contract. Hint: pick hidden inputs that break the most natural memorizer fallback, and let `test_candidate_reward_contract` verify your design" — a new task also needs an entry in `ORACLES` and a branch in `random_inputs`, otherwise `test_random_oracle_agrees_with_correct_candidate` fails with a `KeyError` and the new task cannot be used in the randomized regime at all. The hint should mention the two extra registrations.

4. `code/chapter20_swe_agents/sandbox.py` (module docstring) — "``tasks.FORBIDDEN_TOKENS`` audits that they import nothing capable of network or filesystem access" — the token list covers `os.`, `sys.`, `socket`, `subprocess`, `pathlib`, `shutil`, `open(`, `__import__`, `eval(`, `exec(`, but not `urllib`, `requests`, `http`, `ftplib`, `smtplib`, or a bare `import os`/`import sys` without a dot. The audit is a heuristic token scan, not an isolation guarantee (the README/report are honest that this is a temp-dir + timeout, not a container). Consider rephrasing the docstring to "a heuristic token audit, not a security boundary".

5. `planning/reports/ch20-lab.md` — "Boolean tasks (palindrome) were the hardest to keep strict; hidden inputs were chosen so both constant-True and first-last-character fallbacks fail at least one hidden test (verified: hack hidden rates 0.25-0.75 on that task, never 1.0)" — on the palindrome task the two hack rates are 0.500 (`memorize_true`) and 0.750 (`first_last_heuristic`); 0.25 is the rate of the fizzbuzz hacks, not a palindrome rate. The statement is true in substance ("never 1.0"), but the quoted range does not describe that task.

6. `docs/chapter20_swe_agents/lab.md` (§20.L.2) — "The shortcut candidates implement exactly the failure modes the chapter lists: hardcoding answers to the public examples, plus one shallow heuristic per tricky task (first/last-character match for palindromes, digital root for digit sums)" — Chapter 20.1 lists four failure modes (deleting/skipping tests, hardcoding public answers, breaking uncovered old behaviour, tampering with the test entry point); the lab implements only the second, plus two heuristics that are not on the list. "exactly the failure modes the chapter lists" overstates the coverage; "the chapter's second failure mode, plus two hand-made heuristics" would be accurate.

7. `docs/chapter20_swe_agents/lab.md` (§20.L.3) — "`--reward {all,visible,hidden,randomized}` trains one regime only" — `--reward all` trains three regimes; the sentence should read "selects which regime(s) to train (`all` runs the three regimes)".

8. Not in the diff, but the lab page builds two exercises on it: `docs/chapter20_swe_agents/world-model-and-deep-swe.md` gives DeepSWE's SWE-bench Verified result twice with different values — the text says "42.2% Pass@1 and about 59% with test-time scaling" (Agentica × Together AI), while the table "Achievements of DeepSWE" lists "DeepSWE (ByteDance) 50.0%", and the table in §20.2.4 lists "Code World Model … 65.8% with test-time scaling" and "DeepSWE … 42.2% Pass@1; about 59% scaled". The same section also attributes DeepSWE to ByteDance in one table and to "Agentica × Together AI" in the text, and the "SWE-Lancer (OpenAI) 45.0%" row is not traceable to anything in the page. Since the lab page cites 20.2 in exercises 5 and 6, it would be worth having the chapter owner reconcile these numbers.

## Verdict

This is a careful, well-built piece of work: the sandbox, the REINFORCE-with-baseline update and the 14-task suite are all correct (I checked every candidate's visible/hidden pass rate by hand and by execution, and the shipped contract test's assertions hold), and — importantly — the numbers on the page are real. Re-running the loop with the shipped hyperparameters reproduces the page's two tables to the last digit, so the report's claim that the numbers come from an actual run is credible, and the REINFORCE gradient sign, the running-baseline bookkeeping and the JSON round-trip through the sandbox are all sound. The problems are in the story told about those numbers and in the repository integration. The page's central claim that the hidden and randomized regimes "restore the correct implementations as the unique optimum" is contradicted by its own task data: two "wrong" arms pass the full hidden suite, the randomized alphabet cannot separate `lowercase_only` from the correct vowel counter, and in the reported run the hidden regime ends with 0.997 of the mass on a wrong `binary_search` implementation (hence `resolved` 0.929, not 1.0) — the page never mentions this. The sentence "Their final rows match" contradicts the table directly above it. The seed-to-seed band quoted for the visible row is too narrow (seeds 0–3 give hidden 0.29–0.49), the exercise-3 hint rests on a premise the shipped code contradicts (memorizers are longer than the correct solution on 11 of 14 tasks), and the claim that infrastructure failures are not counted as ability failures is not what `train.py` does. Finally, the page is not in the VitePress sidebar and its "20.L" numbering is incompatible with `scripts/fix-heading-numbers.mjs`, so the deliverable is not mergeable as it stands. Fixing errors 1–7 (data/claim alignment, the two exercise hints, the sidebar entry and the numbering) would make this revision shippable; the remaining items are wording.
