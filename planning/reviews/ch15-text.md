2. `docs/chapter15_grpo/deepseek-dapo.md` — "But for a promising action whose current probability is only 0.01, the lower bound of 0.8 lets it be pushed down to 0.008—almost completely suppressed." — **the mechanism is described backwards.** DAPO's Clip-Higher raises the _upper_ clipping bound (ε*low = 0.2, ε_high = 0.28, i.e. the band becomes [0.8, 1.28]); the lower bound is left at 0.8 and is exactly what stops a token from being pushed down. What limits a promising low-probability token is the \_upper* bound: with ρ ≤ 1+ε = 1.2 its probability can grow at most 20 % per update (0.01 → 0.012), whereas Clip-Higher allows 28 % (0.01 → 0.0128). The table cell "Symmetric upper/lower clipping over-suppresses low-probability actions" is wrong for the same reason (nothing is suppressed by the upper bound). — Suggested fix: rewrite the paragraph around the upper bound, e.g. "with the symmetric band [0.8, 1.2] a token whose probability is 0.01 can only grow to 0.012 per update; Clip-Higher widens the upper bound to 1.28 so rare but promising tokens can be explored."

3. `docs/chapter15_grpo/deepseek-dapo.md` — "Token-level loss lets GRPO distinguish which tokens contributed to the error and which did not." — **mischaracterization of DAPO's third technique.** DAPO's token-level policy-gradient loss changes only the _reduction_ (a token-level average over the batch instead of GRPO's per-response average `1/|o_i| Σ_t`); the advantage is still the sequence-level outcome reward, so no per-token credit signal is created and the model cannot "distinguish which tokens contributed to the error". DAPO's stated purpose is to remove the bias of GRPO's per-response average toward _short_ responses. The chapter's own text says the same thing in another place: 15.1 notes that BNPO "averages all valid batch tokens globally and therefore gives longer responses more weight" — that is precisely what DAPO's token-level loss is. The paragraph as written also contradicts the table row "Sequence-level reward normalization ignores differences between tokens". — Suggested fix: describe token-level loss as "GRPO's per-response average divides the single response-level advantage by the response length, which penalizes long answers; DAPO instead averages over all tokens in the batch, so length no longer distorts the update".

4. `docs/chapter15_grpo/review.md` (Exercise 6, solution code) — "std = rewards.std() # population std, matches the chapter's convention" — **contradicts the chapter's stated convention.** 15.1 says: "DeepSeekMath writes `std` without specifying whether the denominator is $G$ or $G-1$. The example follows the default definition of PyTorch `torch.std` and uses Bessel's correction", and the shipped code map uses `grouped_rewards.std(dim=1, keepdim=True, correction=1)`. The two conventions give different numbers: for `[1.5, 0.0, 1.5, 0.0, 1.0, 1.5, 0.5, 1.5]` the population std is 0.63431 → advantages `[0.8868, −1.4780, …]`, the sample std is 0.67810 → `[0.8295, −1.3825, …]`. Exercise 2 has the same problem (it asks for the population std and answers ±1.4142; under the chapter's Bessel convention it would be ±1.2247). Note that 15.1 itself is already inconsistent — its numpy snippet prints "standard deviation: 0.634" (population) while the prose claims Bessel, and the mermaid diagram uses the Bessel value (0.69 for a 6-sample group). — Suggested fix: pick one convention, state it once in 15.1, make the 15.1 numpy snippet and comment match it, and have Exercises 2 and 6 use (or explicitly contrast with) it.

6. `docs/chapter15_grpo/rl-environments.md` — "To see why, return to the PPO/GRPO objective from [Chapter 15](./grpo-family)" — **wrong target.** The policy-gradient objective quoted immediately below, $\nabla_\theta J(\theta)=\mathbb{E}_{\tau\sim\pi_\theta}[\sum_t A(s_t,a_t)\nabla_\theta\log\pi_\theta(a_t\mid s_t)]$, is in 15.1 (`grpo-practice-and-mechanism.md`), not in 15.4 (`grpo-family.md`, "Improved Methods for GRPO"), which contains no such formula. 7. `docs/chapter15_grpo/grpo-practice-and-mechanism.md` (new "Which KL estimator? k1 versus k3" box) — "**k3 (squared / exponential):**" — **wrong label.** In the standard k1/k2/k3 family the _squared_ log-ratio estimator is k2, $\tfrac12(\log\pi_\theta-\log\pi_{\text{ref}})^2$; k3 is the exponential form $\exp(\Delta)-\Delta-1$. Calling k3 "squared" mislabels the estimator the reader is being told to compare against. The derivation in the box itself is correct (I verified: with $\Delta=\ell^{\text{ref}}-\ell^{\theta}$ and samples from $\pi_\theta$, $\mathbb{E}[\exp(\Delta)]=\sum_v\pi_{\text{ref}}(v)=1$ and $\mathbb{E}[\Delta]=-D_{\text{KL}}$, so both k1 and k3 are unbiased for $D_{\text{KL}}(\pi_\theta\|\pi_{\text{ref}})$). — Suggested fix: "**k3 (exponential):**" and, if the squared estimator is worth mentioning, add it as k2.

8. `docs/chapter15_grpo/review.md` (Exercise 5, solution) — "check: $\ln 1.485 \approx 0.3958$, divided by $3$ is $0.1319$, $\exp(0.1319)\approx 1.141$" — **the intermediate logarithm is wrong**: $\ln(1.485)=0.395415$ (not 0.3958), so $/3=0.131805$ and $e^{0.131805}=1.140886$. ## Doubts

1. `docs/chapter15_grpo/grpo-family.md` — the deleted bullet "**mHC Residual Stability**: Optimization of the numerical stability of the Modified Hamiltonian Monte Carlo (mHC) sampler during long Chain-of-Thought (CoT) training" — the _expansion_ was certainly wrong, but "mHC" is a real component name in the DeepSeek-V3.2 line: **Manifold-Constrained Hyper-Connections**, introduced as a plug-and-play module to stabilize long-CoT training. The report's justification ("No such sampler exists in any verifiable GRPO/V3.2 source") may therefore have removed a real mechanism along with the bogus expansion. — Please re-check the V3.2 technical report: if mHC = Manifold-Constrained Hyper-Connections, the sentence could be rewritten as "V3.2 introduces Manifold-Constrained Hyper-Connections (mHC) to stabilize long-CoT training" instead of being deleted.

2. `docs/chapter15_grpo/grpo-family.md` — "the paper VAPO (Value-based Augmented PPO, [arXiv:2504.05118])" — I can confirm the arXiv id and the venue (ByteDance Seed, April 2025) and the 60.4 AIME-2024 number, but not the expansion "Value-based Augmented PPO"; the paper's title is "VAPO: Efficient and Reliable Reinforcement Learning for Advanced Reasoning Tasks" and I have not seen that acronym expansion in the literature. — Suggest verifying or dropping the expansion.

3. `docs/chapter15_grpo/grpo-family.md` — "This is why GRPO became the mainstream approach in 2024" — GRPO was published with DeepSeekMath in Feb 2024, but its mainstream adoption is generally dated to DeepSeek-R1 (Jan 2025); the same page opens with "From the publication of the R1 paper (2025.01)". Minor chronology wobble, pre-existing.

4. `docs/chapter15_grpo/grpo-family.md` — "making large-scale RL training on a 10,000-card cluster feasible" (GSPO) and "all Qwen3 series … are trained based on GSPO" — the report flags the GSPO _formula_ as unverified but leaves these two claims unqualified; a 10,000-card figure is very specific and I could not verify it offline. Same for the summary bullet's "Byte + Tsinghua" attribution for DAPO.

5. `docs/chapter15_grpo/rl-environments.md` — the AReaL table's "Llama-3-8B on agentic tasks" attribution: AReaL's headline numbers are, as far as I know, from a DeepSeek-V3-671B MoE **math** run (as Chapter 18.4 itself says), so the model size and task type in 15.5 are probably wrong too, not just inconsistent with 18.4. — Please check the paper's Table before shipping either version.

6. `docs/chapter15_grpo/review.md` (Exercise 8) — the diagnostic "entropy falling 4.2 → 1.1 … KL against the reference flat" is unusual: a 3.1-nat collapse of the next-token distribution moves the policy far from the reference, so KL should grow visibly; the solution's "KL flat because the drift is gradual, not a single large step" is a weak explanation. Also, the proposed mechanism ("longer answers get more chances to contain a correct-looking span") predicts _rising_ reward, while the scenario says the reward is flat at 0.85. The intended answer (verbosity-driven collapse with flat external quality) is right, but the given traces do not fully support it — consider adding an explicit "training reward is flat but held-out accuracy is flat too, so the length growth is not buying correctness" or adjusting the numbers (e.g. KL rising) so the diagnosis follows.

7. `docs/chapter15_grpo/grpo-practice-and-mechanism.md` — the new KL box's naming ("the two common per-token estimators … k1 / k3") — the book's k3, $\exp(\ell^{\text{ref}}-\ell^{\theta})-(\ell^{\text{ref}}-\ell^{\theta})-1$, matches veRL's `low_var_kl` ("or k3") and the repo's own `scripts/check-grpo-objective.py` (`delta = ref_logprobs - new_logprobs`), but Hugging Face TRL's `use_bias_correction_kl` is documented as `exp(log_ratio) - log_ratio - 1` with `log_ratio = log π_θ − log π_ref`, i.e. the _opposite_ orientation (for which $\mathbb{E}_{\pi_\theta}[\exp(\Delta')]$ is $\sum_v \pi_\theta(v)^2/\pi_{\text{ref}}(v)$, not 1). Since the box tells readers to "always check which estimator the code uses", it would help to state the orientation explicitly next to the formula.

8. `docs/chapter15_grpo/grpo-family.md` (new "Operating Envelopes") — "if clipped tokens exceed roughly a third of the batch, the rollout batch is stale" — an unsourced threshold; the clipped fraction also depends on the sign distribution of the advantages (with $\hat A<0$ the clip binds _below_ 0.8), so a single numeric cut-off is at best a rough guide. Consider phrasing it as "a rising clipped fraction (and a growing mean $|\rho-1|$) is the signal to refresh", or cite where the number comes from.

9. `docs/chapter15_grpo/rl-environments.md` (new "Retry deduplication") — "keep at most one judged trajectory per (prompt, environment seed) per update" is ambiguous against GRPO's group structure: a prompt needs $G$ distinct rollouts to form a group, so the rule only preserves the group if each of the $G$ rollouts uses a different environment seed. Consider writing "keep at most one judged trajectory per (prompt, attempt id); re-sample the missing members of the group instead of padding it with retries".

10. `docs/chapter15_grpo/financial-tool-calling-grpo.md` (new paragraph) — "If exact match rises while KL spikes or validity falls, the policy is trading format stability for lucky guesses rather than genuinely learning the schema." The second half does not follow: a _falling_ validity means the model is producing _less_ parsable JSON, which is the opposite of "trading format stability". The sentence should read "while KL spikes or response validity falls, the gain is coming from lucky guesses on a subset of prompts, not from a more reliable policy" (and note that validity falling is itself a red flag, not evidence of format trading).

## Verdict

This is a careful, mostly correct revision: the fabricated "Modified Hamiltonian Monte Carlo sampler" was removed, the self-contradictory VAPO-vs-R1-Zero comparison was fixed, several unverifiable venue/attribution claims were softened, the dead cross-references (22.6, 10.5, "Chapter 23") were repointed at pages that really exist, and every numeric example I recomputed — group advantages, the k1/k3 estimates, the clipped-token objective, the GSPO geometric mean, all eight exercise solutions — is arithmetically correct. The remaining problems are of three kinds. First, integration: the new `review.md` is not in the VitePress sidebar and uses a `15.R` label that no other chapter uses and that the heading-sync script cannot parse, and the factual fixes were never recorded in `planning/content-review-notes.md`. Second, technical accuracy inside the writer's own pages: the DAPO "Clip-Higher" explanation is inverted (it is an _upper_-bound change, not a lower-bound suppression) and the DAPO "token-level loss" is mis-described as per-token credit assignment when it is only a change of reduction; the AReaL numbers contradict Chapter 18.4 about which setup produced the 2.77×; the new review page states the _opposite_ std convention from 15.1's prose; and the k3 estimator is labelled "squared". Third, small reference slips (a link to 15.4 for a formula that lives in 15.1, a code file that does not contain the function the exercise cites, a front-matter title that disagrees with the sidebar). Fixing errors 1–7 and 12 would make the revision mergeable; the rest are quick clean-ups, and the doubts are mostly attribution checks that need a network.
