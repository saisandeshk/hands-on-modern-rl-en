3. `docs/chapter18_llm_rl_industrial/lab.md` ("What to look for and why", first bullet of the second item) — "**Learner utilization rises with K.** With one slow worker the learner starves (it blocks on the queue); with more workers the queue stays full and the learner spends its time updating." — the claim is contradicted by the lab's own table and is impossible for this implementation. In `run_throughput`, each worker collects its whole 8000-step budget and then puts exactly **one** shard on the queue (`_mp_worker` exits its loop and calls `queue.put(("shard", ...))` once), so the learner performs exactly K updates over K×8000 collected steps for every K: updates-per-collected-step is constant and the queue never holds more than the K final shards, so it can never "stay full". Using the table's own numbers, busy = util × steady*s gives 0.241 s (K=1), 0.201 s (K=2), 0.414 s (K=4), 0.745 s (K=8), i.e. 0.241 / 0.10 / 0.10 / 0.093 s per update — the utilization is `t_update / t_worker`, and it \_falls* when the per-worker collection time grows (CPU contention): 0.188 → 0.074 → 0.085 → 0.164, with the **highest** value at K=1, the exact opposite of "rises with K". My own re-run reproduces the pattern (util 0.211, 0.155, 0.108, 0.227 for steady_s 1.92, 1.99, 6.35, 6.11 s, i.e. 0.405 / 0.154 / 0.172 / 0.173 s per update). The same contradiction makes Exercise 4 ("Starve, then flood, the learner … At what K does the learner saturate on your machine?") unanswerable: there is no saturation point to find, because the number of learner updates per collected step never changes with K. — Suggested fix: either make the workers stream shards (e.g. one shard per 500 steps) so the queue can back up and the utilization really can rise, or delete the "utilization rises with K" bullet and the saturation exercise and report the measured relation `learner_util ≈ t_update / t_worker` (roughly flat in K, falling when the workers contend for cores).

4. `docs/chapter18_llm_rl_industrial/lab.md` ("Results from a full run", throughput paragraph) — "steady-state collection throughput roughly doubles from 1 to 8 workers (6240 to 14092 steps/s) while spawn/startup cost grows from ~2.4 s to ~4.1 s, so small worker counts show sublinear scaling — the fixed broadcast/spawn cost dominates short runs." — the explanation contradicts the measurement definition: `steps_per_sec = total_steps / (t1 - t0)` where `t0` is the moment the last worker reports `"ready"`, so the spawn/startup cost is excluded from the denominator (the column is even labelled "startup excluded"). ## Doubts

1. Reproducibility of the reported curves is environment-specific, not just seed-specific. My re-run of the same command on this machine reproduces the _structure_ of every table (throughput sublinear in K, all async variants far below the sync baseline, `mean_lag` = 3.833 at delay 4 / 60 updates and 6.56 at delay 8 / 25 updates — I re-derived both from `behaviour_version_at` and they match the page exactly), but not the exact episode returns: the throughput `mean_ep_return` is 21.85/21.62/21.97/21.60 here versus 21.85/21.62/21.87/21.41 in the page (identical for K=1,2 and different for K=4,8). The cause is the action-sampling stream (`torch.distributions.Categorical.sample`), which is not stable across torch releases, so "deterministic per seed" holds on one machine but the tables cannot be reproduced verbatim on another one. Consider stating the torch/gymnasium versions used for the reference run.

2. The absolute level of the "sync baseline" (118.67 greedy return after 60 × 2048 = 122,880 steps) is far below what a healthy PPO reaches on CartPole-v1 (300-500 with the same budget), and the likely cause is in `learner_update`: the critic regresses onto raw Monte-Carlo returns (magnitude = episode length, 100-500) through a trunk shared with the actor, and `nn.utils.clip_grad_norm_(policy.parameters(), 0.5)` then rescales the _joint_ gradient, so the large value gradient shrinks the actor's effective step. If the baseline itself is under-trained and unstable, the "async collapses to 9-22" contrast is partly an artifact of an ill-conditioned learner rather than a clean measurement of staleness cost. Worth either fixing the critic (e.g. normalizing the returns, or a separate value head with its own optimiser) or stating the caveat on the page.

3. `vtrace` mode is labelled "V-trace-style" but the critic target is not the V-trace recursion: the code uses `v_target = V(s) + ρ_tr·(G_t − V(s))` with $G_t$ the Monte-Carlo return, whereas V-trace (Espeholt et al., 2018) uses $r_t + \gamma V(s_{t+1})$ with the truncation applied to the TD residual and bootstrapped values. A direct consequence is that with the default `rho_bar = 1.0` the target collapses to $G_t$ for every sample with $\rho \ge 1$, i.e. the "critic correction" is a no-op for exactly the samples where the ratio is large; only $\rho<1$ samples get a shrunk target. The page's description ("corrects the value target with `rho_tr`") is accurate about the code, but the name overstates the algorithm.

4. The page's run instructions use `.venv/bin/python code/...` while the rest of the book writes plain `python code/...` (e.g. `docs/chapter08_ppo/ppo-bipedal-walker.md:64`, `docs/chapter05_dqn/lunar-lander.md:40`); and the same block first says `pip install -r code/chapter18_llm_rl_industrial/requirements.txt` and then invokes `.venv/bin/python`, an interpreter a reader who followed that install line will not have. Also the runtime statements disagree with each other and with the report: the page says "~5-10 min on a laptop CPU", the README says "at most ~15 min", and the report's timed repeat was 231 s (3.9 min); my re-run of the same command took considerably longer than 231 s on this machine, so the range is optimistic.

5. The report's "Other changes" section says "No new files created; no existing chapter pages touched", but all six files in the diff are new. Read as "created in this session" it is fine, but as written it contradicts `git diff --stat` (6 files, 1202 insertions, 0 deletions) and could mislead a coordinator who assumes the lab already existed in `english-only`.

7. Exercise 1 has a well-defined answer that the page does not give, and it is worth stating because it contradicts the exercise's framing: `--broadcast-every 4 --delay 0` gives the lag pattern 0,1,2,3,0,1,2,3,… (mean 1.50, max 3 over 60 updates) while `--broadcast-every 1 --delay 3` gives 0,1,2,3,3,3,3,… (mean 2.90, max 3) — different lag distributions, and different behaviour versions at the same update (at t=4 the first uses version 4, the second version 1), so the learning curves differ too. Exercise 3's hint is correct: `c_bar` scales the actor gradient (`pg_loss = -(c·A·new_lp)`), `rho_bar` only shrinks the critic target, so `--c-bar 0.5` acts like halving the actor's learning rate while `--rho-bar 0.5` freezes the critic towards $0.5V + 0.5G$.

8. `code/chapter18_llm_rl_industrial/rollout_system.py` — the page says "Every batch carries its `beh_version`; `LagTracker` records `learner_version - beh_version` per update", but the batch field is write-only: `Batch.beh_version` is set in `collect_batch` (line 179) and never read by the learner, which records the lag from the local variable (`tracker.record(t, bv)`, line ~346); only the unit test reads `batch.beh_version`. The values happen to be identical, so the bookkeeping is right, but the "the batch carries its version" story is not what the code does — in a real queue the version would have to travel with the data, which is exactly the point the page is making. Either read `batch.beh_version` in `simulate_training` (e.g. `tracker.record(t, batch.beh_version)`) or drop the field.

## Verdict

The lab is a well-chosen, pedagogically sound addition: the version bookkeeping is correct (I re-derived every `mean_lag`/`max_lag` value in the tables from `behaviour_version_at`), the staleness ratio, the PPO-clip loss and the AReaL `[0.8, 1.2]` reference all match Chapter 18, no claim looks fabricated, and the writer was commendably honest about the truncation _not_ helping at delay 4. But the narrative that was built around the numbers does not survive contact with them. Three of the page's five "what to look for" bullets are contradicted or unsupported by the page's own tables: learner utilization cannot rise with K (each worker sends a single shard, so updates-per-step is constant, and the reported 0.188 → 0.164 is non-monotone with the maximum at K=1), the sublinear steady-state throughput cannot be blamed on spawn cost (the steady-state window excludes startup; the cause is core contention), and the sweep does not show returns degrading with delay (clip reaches its best value, 46.00, at the largest delay). The two mechanism claims that carry the lab's conclusion ("clipping rarely binds", "the bound binds") are inferred from `mean_rho ≈ 1.0`, which is a mean and says nothing about how often the bound binds — the statistic that would settle it, `clip_frac`, is computed by the code and then dropped, and the same is true of the per-update `lags` list that two exercise hints point the reader at. On top of that, the README's two links into `docs/` are broken, one bogus subsection citation (`18.4.4`) survived the report's cleanup pass and is still in the README, the LunarLander exercise cannot run with the chapter's own requirements, the page is not in the sidebar (so it is unreachable, and its "18.L" number is not a number this book uses), and the headline unit test compares two identical code paths and therefore proves nothing. Fix the four narrative bullets against the data, export `clip_frac` and `lags`, repair the two README links, add `gymnasium[box2d]`, register the page as 18.6, and replace the tautological test with a simulation-level comparison; the numbers themselves are reproducible and the lab is worth keeping.
